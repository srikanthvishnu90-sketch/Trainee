# Mass-apply proof: the owner's Telegram script (one real application, start to employer email)

Written 2026-11-02 from the code on `trunk` (handler-career.ts, telegram_jobs.ts, trainee-file/handler.ts, results_page.ts, career_apply_receipts.ts). Nothing here was run against production.
Preconditions, risks and the proof rules: `mass-apply-proof-runbook.md` (A and F must be done first; F1 `CAREER_CLOUD_TEXT_CARDS` is the usual blocker).
Evidence tooling: `scripts/launch/mass-apply-proof.sql` (read-only snapshot) then `scripts/launch/mass-apply-proof-report.ts` (PASS/FAIL per rule).
Use YOUR OWN resume and a role you really want, one Greenhouse, Lever or Ashby posting. LinkedIn, Indeed and Handshake rows only say "Apply there".

**Snapshot command** (owner or a read path the owner grants; `<phase>` is one of before-search, after-search, after-apply, final; `<since>` = the UTC time you send step 1, the same value every time):
`psql "$READ_ONLY_DB_URL" -X -q -A -t -v ON_ERROR_STOP=1 -v me=<your user id> -v phase=<phase> -v since=<since> -f scripts/launch/mass-apply-proof.sql > proof-<phase>.json`

**Run the report:** `deno run -A scripts/launch/mass-apply-proof-report.ts proof-before-search.json proof-after-search.json proof-after-apply.json proof-final.json`
It prints VERDICT: PROVEN (and the word "working") only for a `confirmed` row that has the employer reference (`confirmation_id`), `email_confirmed_at` and a matching unflagged received mail event, plus the full chain behind it. `submitted_unconfirmed` is printed as "SENT, UNPROVEN" however nice the page said thanks. Send the four JSON files and the screenshots to the architect.

**The "yes" that approves a whole batch is not in this script.** Today a typed `yes` (D-MS-1, D-031) only answers a card this same thread showed, within 10 minutes (`YES_WINDOW_MS`), for applications that are already prepared, for example the card from `show my applications`; "yes except 3" and "only 1, 2 and 5" pick a subset. A `yes` straight after a role search that approves the whole batch is being built in another PR; do not test it until that PR is merged and deployed and the architect gives you its exact messages. When it ships, use a new `since` at the time you send the `yes`: rule Y1 then checks that the applications queued are no more than the items the answered card showed, and the `batch` block of the snapshot gives the counts.
